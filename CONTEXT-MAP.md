# Context map

Status: a proposal for review. Nothing here is decided for this repository until its owner accepts it, nothing enforces it, and no code was moved to fit it.

The areas of this repository that work is cut by, so that two agents rarely change the same file. A context is a named area of the code with its paths and its tests. Two rules go with it:

1. An issue names one context on its Work card and stays inside its paths.
2. At most one open issue holds a context at a time.

The method comes from stech.com's design note [`docs/rfcs/plan-to-issues.md`](https://github.com/Art-of-Technology/stech.com/blob/main/docs/rfcs/plan-to-issues.md) (that repository is private), which also defines the Work card. stech.com's map grows epic by epic. This one is a first, coarse cut: 13 wide contexts and `schema`, which cover the main areas of the whole repository. A plan splits a context finer when it first needs to.

The code here is laid out by technical layer, not by area: `src/lib` has 147 entries at its top level, and 225 of the 326 route files under `src/app/api` import `@/lib/prisma` directly. So a context is a list of paths across layers, drawn along the file-name prefixes and route folders that already exist, so that a path tells which context it is in.

A path that is in no context yet is not free for all: add its context first. Paths were checked against commit `eea6b6e` of `main` (21 November 2026).

How to read the table:

- Where a wide glob in one row contains a narrower path in another row, the narrower path wins. So `src/lib/issue-assignee.ts` is in `agent-seats` although `src/lib/issue-*.ts` is in `issues`, and `src/app/(auth)/auth/mcp/**` is in `cli-and-mcp` although `src/app/(auth)/**` is in `workspaces-and-access`. No two rows name the same path at the same depth.
- `src/app/api/apps/auth/<area>/**` is the token API that the CLI, the MCP endpoint and seats call. Its folder belongs to the area's context where the table names it. The folders it does not name (`coclaw`, `docs`, `leave`, `live`, `posts`, `reports`, `user`, `workspace`) stay in `app-api`.
- The Tests column names the files whose names carry the area's prefix. `tests/security` (168 test files) and `tests/render` (29) are also run whole on every pull request by `npm test`, which compares the failures with `tests/known-failures.txt`. Every row has at least one test file of its own, so no row says "none"; the UI of all contexts together has only the 29 files in `tests/render` and `tests/browser/**`.
- With these rows, 802 of the 1,279 tracked files under `src/` and 253 of the 326 API route files are in a context.

## Shared files

These files cannot be owned by one row, because work in many contexts has to change them. Proposed rule, the same as in stech.com: an issue that changes one of them says so on its card under "Shares a file with", with the order, and two such issues are never in the same wave.

- `prisma/schema.prisma` (3,193 lines, 103 models, 43 enums) and `prisma/migrations/**`. Proposed rule, as in stech.com: a schema change is its own small task that holds `schema` alone, gets a security review, and is merged and applied by a person. The model groups by context:
  - `workspaces-and-access`: `User`, `Account`, `Workspace`, `WorkspaceMember`, `WorkspaceInvitation`, `CustomRole`, `RolePermission`

  - `app-api`: the ten `App*` models (`App`, `AppToken`, `AppInstallation`, `AppWebhook` and the rest)
  - `notes-and-context`: `Note`, `NoteTag`, `NoteVersion`, `NoteShare`, `NoteActivityLog`, `NoteTemplate`, `ContextFolder`, `ContextFile`
  - `notifications-and-realtime`: `Notification`, `NotificationPreferences`
  - `git-and-github`: `GitHubIntegration`, `Repository`, `Branch`, `PullRequest`, `PRReview`, `AIPRReview`, `Commit`, `PRCheck`, `Version`, `VersionIssue`, `Release`, `Deployment`, `VersionFile`, `ChangelogEntry`, `GitConnection`, `GitConnectionActivity`

- `content/docs/nav.json`, `package.json` and `package-lock.json`.

Import counts are files under `src/` that import the module as `@/lib/<name>`. How often each file is changed was not measured.

## Open questions for review

1. Is `src/app/api/apps/auth/<area>/**` owned by each area, as mapped, or is the whole token API one surface that `app-api` owns?
2. Should `agent-handoffs` stay a context of its own or be folded into `agent-seats`, given that `src/lib/agent-{seats,runners,mode}.ts` import `src/lib/agent-handoffs.ts` and both use `tests/agents/**`?
3. A milestone is an issue of type `MILESTONE` (`Issue.milestoneId`): do `src/lib/issue-milestones.ts` and `src/app/api/projects/[projectId]/milestones/**` belong to `projects-and-views`, as mapped, or to `issues`?
4. Do the seat and worker parts of the CLI (`packages/cli/src/{seat-run,worker,worker-runner,worker-service,coordinator,inbox-watch}.mjs`) belong to `cli-and-mcp`, as mapped by folder, or to `agent-seats` and `agent-handoffs` by subject?
5. Should `content/docs/agents/**` (13 pages on seats and runners) stay in `public-docs`, or should each area own its pages so that a change and its documentation are one issue?
6. Forge is in no context, but 29 files import `src/lib/forge/legacy-write-guard.ts`: is Forge its own context, part of `issues`, or on its way out?
7. `projects-and-views` is the widest row (152 files): split it now into projects and statuses, views, and planning, or when a plan first needs it?
8. Are the two proposed rules accepted here: a schema change is its own task that a person merges and applies, and, as in stech.com, `production` (deploys by tag through `.github/workflows/deploy-*.yml`, secrets, machines) is a person's context with no paths?
