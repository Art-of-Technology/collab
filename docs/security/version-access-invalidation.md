# Saved version authorization

Migration `20260924130000_version_access_invalidation` adds one non-null Boolean column, `Version.issueAccessInvalidated`. No tables, indexes, foreign keys, or saved content are removed or rewritten. Existing versions receive `true`, because their complete historical issue authorization scope cannot be reconstructed from surviving links. New versions default to `false`.

Six PostgreSQL functions and triggers retain and propagate this flag. They invalidate versions on VersionIssue unlink/reassignment; Issue deletion or workspace/project changes; Project deletion or workspace changes; and ProjectStatus deletion or project changes. Status transitions between two statuses in the same project retain validity. Other status-reference changes invalidate it. Invalidation propagates to child versions, is inherited from an invalidated parent, and cannot be cleared by an ordinary update. The existing full issue predicate continues to govern current links.

The shared version/release read predicate requires `issueAccessInvalidated = false`. Legacy or invalidated versions, releases, version-file JSON, and saved AI prose stay stored but are unavailable through these readers, including activity/dashboard projections. Re-linking an issue, regaining membership, or updating saved text does not reauthorize invalidated history.

An authorized user can POST `{ "versionId": "...", "regenerate": true }` to `/api/github/repositories/[repositoryId]/generate-changelog`. This deliberately generates a separate PENDING replacement version, returned as `versionId` alongside `sourceVersionId`. It uses only current linked issue keys, titles and types, requires at least one linked issue and full access to every input, and never selects old AI output, release prose, commits or PR descriptions. The original version, releases and files are preserved and are not relinked or reset. The replacement has a valid SemVer prerelease identifier in the reserved `recovery` environment, excluded from canonical version selection and development promotion. It remains reviewable through the version reader. The replacement contains new summary/changelog output and freshly authorized issue links; it does not publish a release or activate a version file. Sources without surviving authorized inputs cannot be regenerated through this path.

Generation runs outside a database transaction. Before saving or returning output, a short transaction locks the source version, repository, referenced issues/statuses/projects/workspaces, user, and that user's account/membership rows, rechecks current identity and repository/issue access, and compares the selected input snapshot. The user row is locked FOR UPDATE so foreign-key-backed Account inserts cannot change mapping cardinality before commit. Concurrent changes discard the result. Output, current links and the replacement's validity commit atomically. Lock conflicts or failed rechecks create no replacement. No trigger is bypassed and invalidation remains irreversible for the original record.

Bootstrap and restore inventories must include this migration's column and all six trigger/function pairs. Prisma client generation or `db push` alone does not install these triggers. Restore flags with saved data and install triggers before permitting writes. This source revision changes the issue invalidation function's same-project status condition; it adds no further schema objects for regeneration. Install the final migration from this branch for a new bootstrap. An already provisioned test database needs a reviewed function replacement or rebuild, not a checksum edit. The existing notification migration `20260924120000_notification_tenant_scope` is unchanged. No live migration is part of this source repair.
